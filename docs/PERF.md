## 5. 结论

- **目录解析**：冷解析 679.4 ms – 2.47 s；按目录章节线性折算 100 章 165.7 ms – 747.3 ms，§15.4 目标 < 500 ms，未达标（1 本超目标）。解包与 OPF 是固定开销，线性折算只作量级参考；解析完成后命中磁盘缓存。
- **CSS 构建**：单 provider 冷构建 3.35 s – 4.42 s（目标 < 200 ms，未达标）；fallback 三家均分 3000 段 2.26 s – 2.61 s（目标 < 500 ms，未达标）；三家各持 3000 条（9000 条加载）5.65 s – 6.35 s（无目标）。分解：entries 读取（JSON 解码 + 去重）1.23 s – 1.38 s，同参数命中 1.8 ms – 2.2 ms——阅读中重绘不贵；解码只在冷构建/导入后付一次，改字号/换颜色/换字体由预编译模板替换样式（`--overlay` 32.3 ms）；切换显示服务会换模板键，切换后的下一次构建会重建一次（约 0.3–0.85 s，见 §7），冷启动 56.2 ms。
- **MCP 导入**：3000 段 2.69 s – 2.80 s，§15.4 目标 < 5 s，达标。
- **锚点页表**：单章冷解析 150.3 ms – 620.5 ms（基线，无 §15.4 目标）；取锚点最多的章节，最重一章有 23 条 TOC 锚点。CREngine 的逐锚点 `getPageFromXPointer` 探测未计入，真机阅读时每章另加 N 次渲染器调用。
- **overlay 体积**：单 provider 940 KB（§15.4 参考 3,000 段 0.8–1.5 MB）；fallback 均分与全量两行各是三份 entries 之和；entries 每段都带 source/translation/xpointer。

## 6. 口径与限制

- **outline**：每次删除 `data/cache/dualtranslate/outline/<hash>.json` 后冷解析；「100 章 ≈」= 中位数 × 100 / 目录章节数（线性折算）。解包、OPF 解析和 spine 映射是固定开销，折算只用于和 §15.4 的 100 章目标对照，不作为精确预测。前面的书形状探测已读过同一文件，文件页缓存是热的。
- **CSS**：合成 3000 条 entries，selector 采用生产写法（`DocFragment[Source="…"] > body > div:nth-of-type(n) > p:nth-of-type(n)`，约 1% 为列表父项的 `… > ol:nth-of-type(1)::before`，各生成 3 条规则）；每次 `Overlay.clearCssCache()` + `Overlay.clearEntriesCache()` 后 `Overlay.buildCss`（冷构建包含 entries 解码）。fallback 有两个夹具：① §15.4 口径的「3,000 段分给三家」（1,000/1,000/1,000，selector 互不相交，合并后 3,000 条规则）；② 三家都翻完整本（各 3,000 条，9,000 条加载、合并后仍是 3,000 条规则），这是存储与 JSON 解码的最坏形态，只报数不判定；三家各翻不同段落会得到 9,000 条规则，那等价于一本 9,000 段的书，不在 3,000 段口径内。「entries 读取」是同一份文件的 JSON 解码 + 去重；「CSS 命中」是 entries 落盘超过 3 秒后同参数再调用（阅读中翻页/重绘的稳态）。注意「冷构建」含解码，真机还会计入一次模板编码/写盘（`--overlay` 839.0 ms，其中约 0.25 s 是模板编码/写盘）；纯解码 + 渲染约 0.61 s。生产中改字号/换颜色/换字体由模板替换样式，只要 32.3 ms；切换显示服务会换模板键、重建一次（约 0.3–0.85 s）。冷启动 56.2 ms，见 §7。同一份 entries 拆成三份后 JSON 解析会明显变快（LuaJSON 1.3.5 的大文档开销），因此「三服务均分」行低于单 provider 行是文件布局差异，不代表 fallback 更快。CSS 夹具与书内容无关；同轮不同书之间的差异与夹具无关，判定按整轮最大值。
- **导入**：`Store.importResult` 全链路（书锁、SQLite 事务、entries/manifest/signal 写入）；每次前清空该书 overlay 目录与 DB 行，但复用同一个基准库（WAL 与页缓存是热的），不等价于空库首次导入。
- **锚点页表**：`Epub.chapter_anchor_paths` 冷解析目录锚点最多的 5 个章节（各不同，3 槽 LRU 不会命中），中位数为单章成本；这是最坏单章，不是均匀抽样。CREngine 的 `getPageFromXPointer` 探测（每章 N 次）无法在 headless 复现，未计入。
- **未覆盖（本表）**：章节选择器打开（< 1 s）、DB v3 迁移（100k 行 < 2 min，3.3.1 起）、内存增量
  （< 20 / 40 MB）与「相对旧版不劣化 20%」的基线不在本表，分别由
  `tools/bench.lua --migrate` / `--memory`、`tools/probe_picker.lua` 与 v3.2.2 基线树
  单独测量，见 §8。

**RSS A/B**（同一本书，3,133 条规则，字体 16 → 22 px）：

| 时点 | VmRSS |
| --- | --- |
| 开书后稳定 | 94.4 MB |
| 改字号 + `refreshDocumentStyles` 后 | 101.8 MB（+7.4 MB） |
| 关闭插件样式 / 再开启（同一进程） | 111–130 MB 间波动，旧表未立即释放 |

读数含义：

- **解码仍是纯冷构建的大头**：无模板时 839.0 ms，其中约 610 ms 是 entries 解码
  + 渲染，约 0.25 s 是模板编码/写盘（只在模板缺失时付；写入失败后本进程不再重试，
  但内存模板仍保留）。导入后预热模板，首次打开即可走 56.2 ms 的冷启动路径。
- **模板替换取代了解析缓存热路径**：3.2.1 的「样式变化（entries 命中）」111.9 ms
  被 32.3 ms 的模板替换取代；同参数命中仍是 2.3 ms。`clearCssCache` 只清内存 CSS，
  不清模板，也不清 entries（三者独立）。
- **`setStyleSheet` 本身很小**（9 ms vs 26 ms，随表大小略增，但不是瓶颈）。
- **没有观察到整书重排**：页数和当前页在重绘前后一致；`getPageCount()` 在重绘前
  读的是缓存（0.0 ms）。
- **强制重绘 1.2–1.4 s 与 CSS 大小无关**，是 e-ink 首帧/整屏刷新的成本。
- **内存**：本轮开书后 94.4 MB，改字号只 +7.4 MB，未复现历史探针的 +96 MB
  （探针从「无插件样式」切到全书表，起点不同）；关闭/开启插件样式时 CREngine
  不立即释放旧表，RSS 在 111–130 MB 间波动。CLI 直接开书的实例在 `onClose` 后
  进程退出，无法在文件管理器场景测「关书回落」；512 MB 设备上仍应避免频繁换表。
  Lua 侧 CSS 只保留一份：`document._dualtranslate_overlay_css` 持有缓存中同一对象
  的引用，不再拼一份 `extra_css` 常驻；另有一个进程级模板缓存（最近一本，约 1.2 MB
  静态文本 + 47 KB 索引），用于重复换字号。
- **按章 CSS 已删除**（3.2.2）：全书模板替换 32.3 ms 已低于按章时代的 111.9 ms，
  按章还要在跨章时多付一次换表和内存，实验过滤与 11 项测试一并下线。
- **每本书只保留一份模板**：切换显示 provider 或 fallback 会覆盖旧模板，切回时
  需要重新渲染/编码/写盘（约 0.3–0.85 s，取决于解析缓存是否还在）。这是有意的存储
  取舍；频繁来回切的用户会看到一次重建，而不是多份 1.2 MB 模板常驻。
- **磁盘回收**：读取模板/打开书时 touch mtime；开书 10 s 后删除 30 天未使用的模板，
  并按 50 MB 总量上限从最旧开始删（跳过当前书，只删 `css-template.css`，每轮最多
  20 份，避免一次 unlink 太多造成前台顿挫；未删完的下次开书且距上次 ≥6h 后继续，
  同一会话不追赶）。被回收的书每次重开多付一次冷构建（约 0.84 s），之后回到
  56.2 ms 的模板路径。1.2 MB 的重书超过约 41 本时，50 MB 上限会让最旧的一本周期性
  重建；普通书模板远小于 1.2 MB（Pride 的全书 CSS 95 KB，模板同量级），多数用户不会触顶。回收做一次
  全量 `lfs.dir` + 每书几次 stat + 最多 20 次 unlink；常规书库毫秒级，上千本时
  可能几十毫秒，但不在首帧路径上。
- 版本串里的 `kindlepw2` 是构建名，Voyage 也用这个构建，不代表机型。

## 8. §15.4 剩余验收（3.3.0 收口）

> 本节补 §6 列出的缺口：章节选择器打开、DB v3 迁移、真 80+ 章目录解析、
> fallback 三服务内存、「相对旧版不劣化 20%」的基线，以及 3.3.1 补的关书 RSS 回落。
> 设备与 §1 相同，每项按同一口径取中位数；单次读数不作结论。

### 8.1 章节选择器打开（真机阅读器内）

`tools/probe_picker.lua` 经 httpinspector 的 `dofile` 在**正在运行的阅读器进程**里执行，
清掉目录内存缓存与 entries 解析缓存后取 5 次中位数（`open_ms` 为 3 次）：

| 书 | 行数 | 目录解析 | 覆盖度 | 菜单项 | 点开（含 `Menu:new`） | RSS |
| --- | --- | --- | --- | --- | --- | --- |
| JavaScript for Impatient Programmers | 356 | 28.3 ms | 2.3 ms | 4.6 ms | **61.2 ms**（60.0 / 61.2 / 245.4） | +1.2 MB |
| 吴军作品 | 796 | 76.2 ms | 0.6 ms | 9.2 ms | 86.0 ms（只算构建，未切换文档） | — |

- 计时用 `clock_gettime`（墙钟），与 `tools/bench.lua` 同源；`open_samples` 里有一次
  245 ms 的离群值（菜单首帧与刷新），中位数按 3 次取。
- 目录解析是**磁盘缓存命中**；冷解析另见 §3（646 章的吴军作品 2.47 s），第一次打开
  一本书时选择器会先显示「正在解析目录…」，之后回到上表。
- 结论：**达标**（目标 < 1 s）。真机 `open_ms` 为 61.2 ms；796 行那本只测到构建合计
  86.0 ms（未切换文档，不含 `Menu:new`）。行数从 356 增到 796，菜单项只从
  4.6 ms 增到 9.2 ms；`Menu:new` 的布局只看可见行，与总行数无关。

### 8.2 DB v3 迁移（100k 行）

`tools/bench.lua --migrate --rows 100000`：建 40 本书、按书分组的 v2 库，计时
`Store.migrateIfNeeded`（含 checkpoint、`.bak` 复制、重建表与 3 个索引）：

| 行数 | 墙钟 | CPU | `.bak` | 其中 `.bak` 复制 |
| --- | --- | --- | --- | --- |
| 10,000 | 2.79 s | — | 2.2 MB | — |
| 100,000 | 91.4 s / 103.5 s（两次单跑） | 8.7 / 8.9 s | 22.7 MB | 6.9 s（暖缓存下限） |

- 结论：按原目标 **< 10 s 未达标**；3.3.1 已把 §15.4 的目标改为「100k 行 < 2 min」，
  按新目标 91–104 s 达标。墙钟减去 CPU 与复制，仍有约 76–88 s 是 eMMC/FUSE 的
  页写等待：这次迁移要写新表（约 15 MB）+ 3 个索引（约 25 MB）+ `.bak`（23 MB，
  顺序复制只要 6.9 s），而 `/mnt/us` 上 SQLite 的 4 KB 页写只有约 0.5 MB/s（`dd`
  顺序写能到 5 MB/s，页级随机写不行）。
- 试过但没有进代码：`PRAGMA cache_size=-32768` 仍是 87 s（无改善）；把 `INSERT` 改成
  按新主键 `ORDER BY` 后进程在 55 s 静默退出（疑似内存压力），已回滚。迁移是风险最高
  的代码路径，没有把握的改动不留在里面。
- 3.3.1 已采用前一个方案：§15.4 的目标改为「100k 行 < 2 min（一次性，有 `.bak`）」，
  启动时先 `Cache:peekSchema()` 只读判断，再显示「正在升级译文缓存…请不要退出 KOReader」
  并强制重绘，迁移完成后关闭提示。10 万行约是一本 646 章书（16k 段）的 6 倍，属于长期
  积累；一次性等 1.5 分钟可以接受，真正的风险是升级时用户以为卡死而强杀进程。后台迁移 +
  进度条仍可作为后续增强。

| 形态 | 峰值 RSS（VmHWM） | 构建后 Lua 堆 | 规则 |
| --- | --- | --- | --- |

### 8.4 真 80+ 章书的目录解析

§3 的「100 章 ≈」是从 331 / 410 / 335 章的整本线性折算，会放大解包这本大书的固定开销。
找两本目录章节就在 80 附近的真书复测（`--runs 5`，删磁盘缓存后冷解析）：

| 书 | 大小 | spine | 目录章节 | 实测 | 100 章折算 |
| --- | --- | --- | --- | --- | --- |
| 人类简史三部曲（套装全3册） | 9,091 KB | 83 | 83 | 371.8 ms | 448.0 ms |
| Docker —— 从入门到实践 | 496 KB | 83 | 81 | 88.0 ms | 108.6 ms |

- 结论：**达标**。真实 83 章的书折算 100 章为 448 ms（< 500 ms）；Docker 只有 108.6 ms。
  §3 的 747 ms 是 39 MB / 331 章那本书的折算值，解包与 OPF 是固定开销，章数越多摊得越薄；
  这两本真书说明「100 章 < 500 ms」在典型书上是成立的，只有超大文件 + 目录章节占比低时
  才会超。后续引用请同时给出「实测章数」和「文件大小」，不要只报折算值。

### 8.6 关书 / 换书 RSS 回落（Voyage）

3.3.1 的阅读器进程（Kindle Voyage，重启后加载 3.3.1 代码），经 httpinspector 的
`ui/switchDocument` / `ui/closeDocument` 在同一进程里开书、换书、关书，每次
`collectgarbage("collect")` 后读 `/proc/<pid>/status`：

| 阶段 | VmRSS | VmHWM |
| --- | --- | --- |
| 冷启动打开 A（JavaScript for Impatient Programmers） | 83.5 MB | 86.9 MB |
| 换到 B（Pride and Prejudice） | 68.0 MB | 86.9 MB |
| 换回 A | 67.8 MB | 86.9 MB |
| 再换到 B | 63.8 MB | 86.9 MB |
| 再换回 A | 63.9 MB | 86.9 MB |
| `closeDocument` 关书 | 63.9 MB | 86.9 MB |

- 换书时旧书的 CREngine 表被释放：A→B 回落 15.5 MB；之后 A/B 循环的 RSS 没有回到第一次
  打开 A 的 83.5 MB，也没有逐次增长（63.8–67.8 MB），VmHWM 全程 86.9 MB 不变。
- 关书后进程停在 63.9 MB，没有出现「关书仍保留整本 A」的现象。早先在 3.3.0 进程上做的
  同一循环（起点 123 MB，那是读过很久的会话）也观察到 A→B −33 MB、A/B 循环
  80–82 MB 且 HWM 不变。
- 口径：这是单次会话的绝对值，Lua 堆不会全部还给 OS；判据是「循环不增长 + HWM 不升高」，
  与 §15.4 的 20% 相对判据不同。
- 复跑：重启阅读器后依次请求 `/koreader/ui/switchDocument/'<URL 编码后的书路径>'`、
  `/koreader/globals/collectgarbage/collect`，再从 SSH 读 `/proc/<pid>/status`；结束时用
  `/koreader/ui/closeDocument/`。不修改书或译文。
